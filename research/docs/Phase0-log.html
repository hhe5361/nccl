Phase 0

Phase 0 구현 로그

research/docs/cumulative-cts-experiment-plan.html의 Phase 0 (Correctness / Instrumentation)에 맞춰, NCCL 동작을 바꾸지 않고 실험용 구조화 로그를 추가한 기록이다. 이 문서는 어떤 파일을 수정했는지, 어떤 로그가 생기는지, 어떻게 빌드/실행/수집하는지를 정리한다.

Goal: observability only
No admission policy change
Runtime toggle: NCCL_PHASE0_LOG=1

1. 이번 Phase 0에서 한 일

  • 기존 per-slot CTS 동작은 유지했다.
  • 실험용 로그를 런타임 플래그로만 켜지게 만들었다.
  • 다음 이벤트를 추적 가능하게 했다.
    IB_CTS_ISSUE, IB_SEND_POST, IB_SEND_COMPLETE, PROXY_SEND_POST, PROXY_SEND_DONE, PROXY_RECV_POST, PROXY_RECV_NET_DONE, PROXY_RECV_VISIBLE, PROXY_RECV_CONSUMED
  • 로그 포맷은 모두 PHASE0 event=... key=value ... 한 줄 형식으로 맞췄다.
즉 Phase 0의 목적은 정책 실험이 아니라, 이후 Phase 1~4에서 필요한 데이터를 NCCL 내부에서 직접 뽑아낼 수 있는 관측 기반을 만드는 것이다.

2. 수정한 파일과 역할

파일 수정 내용 목적
src/transport/net.cc NCCL_PHASE0_LOG 파라미터 추가, proxy 계층 로그 helper 추가, send/recv progress 경로에 structured log 삽입 posted / received / transmitted / done frontier, slot visibility, recv consumption을 추적하기 위함
src/transport/net_ib/p2p.cc IB CTS issue, send post, send complete 지점에 structured log 삽입 reverse control path와 실제 RDMA data send를 추적하기 위함
이번 단계에서는 동작 변경이 없고, 로그만 추가했다.

3. 추가된 런타임 파라미터

환경변수 기본값 의미
NCCL_PHASE0_LOG 0 1이면 실험용 structured log 출력
NCCL_DEBUG 기존 NCCL 설정 사용 Phase 0 로그는 INFO(NCCL_NET,...)로 출력되므로 INFO 이상 필요
NCCL_DEBUG_SUBSYS 기존 NCCL 설정 사용 Phase 0 로그를 보려면 최소 NET 포함 필요
NCCL_DEBUG_FILE stderr 노드별 로그 파일로 분리 저장할 때 권장

4. 로그 이벤트 정의

이벤트 계층 의미
IB_CTS_ISSUE IB transport receiver가 sender의 CTS FIFO로 CTS를 RDMA write 한 시점
IB_SEND_POST IB transport sender가 CTS를 확인하고 실제 RDMA write를 post 한 시점
IB_SEND_COMPLETE IB transport sender 측 send request completion 시점
PROXY_SEND_POST proxy proxy가 ncclNet->isend()를 성공적으로 발행한 시점
PROXY_SEND_DONE proxy send request 완료 후 slot이 recycle 가능한 방향으로 진행된 시점
PROXY_RECV_POST proxy proxy가 ncclNet->irecv()를 post 한 시점
PROXY_RECV_NET_DONE proxy 네트워크 수신이 완료되어 해당 slot payload가 도착한 시점
PROXY_RECV_VISIBLE proxy recvTail가 갱신되어 GPU가 해당 데이터를 볼 수 있게 된 시점
PROXY_RECV_CONSUMED proxy GPU 소비가 반영되어 recv request가 회수되는 시점

5. 로그 포맷

모든 Phase 0 로그는 한 줄에 하나의 이벤트를 기록하며, 후처리 편의를 위해 key=value 형식으로 통일했다.

PHASE0 event=IB_CTS_ISSUE reqId=17 slot=1 nreqs=1 ctsBytes=32 idx=18 addr=0x7f... rkey=0x1234 qp=552 comm=0x... PHASE0 event=IB_SEND_POST reqId=17 slot=1 nreqs=1 size=131072 remoteIdx=18 tag=3 comm=0x... PHASE0 event=IB_SEND_COMPLETE reqId=17 slot=1 size=131072 nreqs=1 comm=0x... PHASE0 event=PROXY_SEND_POST rank=0 peer=5 channel=2 slot=1 coll=Send collApi=AllToAll algo=RING proto=SIMPLE size=131072 base=0 posted=2 received=0 transmitted=1 done=0 nsteps=32 PHASE0 event=PROXY_RECV_VISIBLE rank=5 peer=0 channel=2 slot=1 coll=Recv collApi=AllToAll algo=RING proto=SIMPLE size=131072 base=0 posted=2 received=2 transmitted=2 done=1 nsteps=32
parsing 시에는 event=...를 기준으로 이벤트 종류를 나누고, 나머지 key=value를 공통 스키마로 읽으면 된다.

6. 이 로그로 무엇을 볼 수 있나

CTS count / CTS bytes

IB_CTS_ISSUE 개수와 ctsBytes 합계를 세면 된다. Phase 2에서 cumulative CTS 도입 시 baseline과 직접 비교할 수 있다.

Control-to-data lag

IB_CTS_ISSUE와 IB_SEND_POST 사이 시간 차이를 계산하면, CTS 도착 이후 sender가 실제로 얼마나 빨리 전송을 시작하는지 볼 수 있다.

Slot pipeline frontier

proxy 로그의 posted / received / transmitted / done를 이용해 slot occupancy와 pipeline depth를 재구성할 수 있다.

Recv visibility chain

PROXY_RECV_POST → PROXY_RECV_NET_DONE → PROXY_RECV_VISIBLE → PROXY_RECV_CONSUMED 순서로 receiver-side lifecycle을 직접 볼 수 있다.

7. 빌드 방법

실제 실험은 CUDA toolkit이 정상 설치된 cluster/node에서 수행해야 한다.

cd /mnt/c/Users/hyoeun/dev/nccl make -j src.build
현재 로컬 환경에서는 cuda.h, cuda_runtime.h가 없어 전체 빌드가 실패했다. 따라서 최종 빌드 검증은 실제 실험 환경에서 다시 해야 한다.
Observed local build blocker - transport/net.cc compile path: missing cuda.h - transport/net_ib/p2p.cc compile path: missing cuda_runtime.h

8. 실행 방법

8.1 공통 환경변수

export NCCL_PHASE0_LOG=1 export NCCL_DEBUG=INFO export NCCL_DEBUG_SUBSYS=NET export NCCL_DEBUG_FILE=/tmp/nccl-phase0.%h.%p.log

8.2 조합별 실험을 강제로 나누고 싶다면

# 예시: Ring + Simple export NCCL_ALGO=Ring export NCCL_PROTO=Simple # 예시: Ring + LL export NCCL_ALGO=Ring export NCCL_PROTO=LL # 예시: Tree + LL128 export NCCL_ALGO=Tree export NCCL_PROTO=LL128

8.3 권장 실행 workload

  • 초기 validation: nccl-tests의 all_reduce_perf, alltoall_perf
  • 논문용 characterization: collective × algorithm × protocol × message size sweep
  • cluster topology 비교: 4-node intra-rack / 8-node cross-rack 분리 실행

8.4 예시 실행

# 예시: 8노드 cross-rack AllReduce characterization NCCL_PHASE0_LOG=1 \ NCCL_DEBUG=INFO \ NCCL_DEBUG_SUBSYS=NET \ NCCL_DEBUG_FILE=/tmp/nccl-phase0.%h.%p.log \ NCCL_ALGO=Ring \ NCCL_PROTO=Simple \ mpirun -np 8 -N 1 ./all_reduce_perf -b 64K -e 256M -f 2 -g 1 # 예시: 8노드 AllToAll characterization NCCL_PHASE0_LOG=1 \ NCCL_DEBUG=INFO \ NCCL_DEBUG_SUBSYS=NET \ NCCL_DEBUG_FILE=/tmp/nccl-phase0.%h.%p.log \ NCCL_PROTO=Simple \ mpirun -np 8 -N 1 ./alltoall_perf -b 64K -e 256M -f 2 -g 1
all_reduce_perf, alltoall_perf는 이 repo가 아니라 보통 nccl-tests 쪽에서 제공된다. 실제 cluster에서는 그 바이너리를 사용하면 된다.

9. 로그 수집과 후처리

9.1 Phase 0 이벤트만 추리기

rg "PHASE0 event=" /tmp/nccl-phase0.*.log > phase0-events.log

9.2 이벤트별 개수 세기

awk '{ for (i=1; i<=NF; i++) { if ($i ~ /^event=/) { split($i, a, "="); cnt[a[2]]++; } } } END { for (k in cnt) print k, cnt[k]; }' phase0-events.log | sort

9.3 CTS 패킷 수 / 바이트 합계

awk '{ ev=""; bytes=0; for (i=1; i<=NF; i++) { if ($i ~ /^event=/) { split($i, a, "="); ev=a[2]; } if ($i ~ /^ctsBytes=/) { split($i, a, "="); bytes=a[2]; } } if (ev == "IB_CTS_ISSUE") { cnt++; sum += bytes; } } END { print "cts_count", cnt; print "cts_bytes", sum; }' phase0-events.log

9.4 proxy frontier 추출

awk '/PROXY_/ { print $0 }' phase0-events.log > phase0-proxy-frontier.log
이후 Python/pandas에서 posted, received, transmitted, done를 읽어 timeline plot이나 occupancy plot으로 만들면 된다.

10. Phase 0 완료 기준

  1. NCCL_PHASE0_LOG=0일 때 기존 동작과 결과가 같아야 한다.
  2. NCCL_PHASE0_LOG=1일 때 structured log가 출력되어야 한다.
  3. AllReduce와 AllToAll 각각에서 CTS issue / send / recv lifecycle 이벤트가 모두 보여야 한다.
  4. 4-node와 8-node 실행에서 로그를 분리 수집할 수 있어야 한다.
  5. 후처리 스크립트로 최소한 CTS count와 proxy frontier가 계산되어야 한다.
