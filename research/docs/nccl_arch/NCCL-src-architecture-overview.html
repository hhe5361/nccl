NCCL src Architecture

NCCL src/ 아키텍처 개요

이 문서는 src/ 전체를 기능별 계층으로 다시 묶어서 설명한다. 목표는 "API 호출이 어디서 계획되고, 어떤 상태가 comm/channel/connector/plan/proxy를 지나 GPU kernel과 transport로 흘러가는가"를 큰 그림으로 잡는 것이다.

분석 범위: src/ 총 파일 수: 387 핵심 축: init / graph / enqueue / proxy / device / transport 작성일: 2026-04-13

한 줄 요약

1. Public API

collectives.cc와 group.cc가 사용자 요청을 ncclInfo, task queue, group job으로 바꾼다.

2. Communicator / Topology

init.cc, bootstrap.cc, graph/*, channel.cc가 rank 집합, topology, ring/tree/NVLS/CollNet 구조를 만든다.

3. Planner

enqueue.cc가 task를 채널별 work와 proxy op로 분해하고, kernel args와 launch plan을 만든다.

4. Proxy / Transport

proxy.cc와 transport/*가 host-side progress를 수행하며, P2P, SHM, NET, CollNet, NVLS 경로를 실제로 연결한다.

5. Device Kernel

device/*는 채널당 block 단위로 실행되며, loop/chunk/slot 수준의 collective primitive를 수행한다.

6. Cross-Cutting

plugin/*, register/*, rma/*, misc/*, ras/*, include/*가 확장성, 버퍼 등록, 진단, 플랫폼 지원을 맡는다.

가장 중요한 관찰은 이것이다. NCCL은 단순한 kernel 집합이 아니라, host planner + proxy progress engine + device primitive library가 결합된 런타임이다.

먼저 잡아야 하는 핵심 객체

객체 어디에 있나 역할 이 객체를 이해하면 보이는 것
ncclComm include/comm.h communicator 전체 상태. topology, channels, planner, proxy, plugin, mem manager를 다 품는다. NCCL이 왜 "상태 머신"처럼 보이는지
ncclChannel include/comm.h 실행 lane. ring/tree/NVLS peer 관계와 per-channel peer endpoint를 보유한다. Figure 3의 channel과 kernel의 blockIdx.x 매핑
ncclChannelPeer, ncclConnInfo include/device.h peer별 send/recv endpoint와 slot buffer, head/tail, connFifo 메타데이터를 표현한다. slot pipeline과 transport staging 구조
ncclTask* include/comm.h API 호출이 enqueue 단계에서 변환된 host-side 작업 단위다. user API가 바로 kernel launch로 가지 않는 이유
ncclKernelPlan include/comm.h 하나의 launch batch. channel mask, work batch, kernel args, proxy ops를 담는다. planner가 실제 launch 단위로 무엇을 묶는지
ncclProxyOp, ncclProxyArgs include/proxy.h host proxy가 수행할 send/recv/progress 단위다. network progress가 kernel 밖에서 어떻게 계속되는지
Primitives<...> device/primitives.h device-side send/recv/reduce/copy 미세 연산을 protocol별로 구현한다. all_reduce.h와 prims_simple.h의 관계
구조만 먼저 기억하면 된다. comm가 전체 컨테이너이고, channel이 lane이며, connector/conn가 peer endpoint이고, plan이 launch batch이며, proxy가 host progress를 담당한다.

초기화 흐름

communicator를 만드는 경로와 collective를 실행하는 경로는 다르다. 먼저 ncclCommInitRank 시점에 전체 통신 구조가 만들어진다.

ncclGetUniqueId / ncclCommInitRank -> init.cc : global env init, bootstrap net init -> bootstrap.cc : OOB socket/net bootstrap, peer info exchange -> init.cc : peerInfo allgather, local/node rank derivation -> graph/topo.cc + xml.cc : hardware/topology model build -> graph/paths.cc : GPU/GPU, GPU/NIC path classification, P2P/GDR checks -> graph/search.cc + tuning.cc : ring/tree/CollNet/NVLS graph search and tuning -> graph/connect.cc : prev/next/up/down/head mappings materialized into channels -> channel.cc : host/device channel peer tables allocated -> transport.cc : per peer / per channel transport selection and connect exchange -> proxy.cc + plugin/* : proxy state, net plugin, profiler, tuner, gin init -> devComm copied to GPU memory -> communicator ready
  1. collective 이전에 topology와 graph가 먼저 결정된다. 이 단계가 끝나야 어떤 channel이 어떤 peer와 어떤 transport를 쓰는지 정해진다.
  2. graph/*는 단순 탐색이 아니라, 실제 bandwidth/path 제약을 고려해 ring/tree/NVLS 배치를 산출한다.
  3. transport.cc는 각 channel-peer에 대해 P2P, SHM, NET, CollNet 중 무엇을 쓸지 선택하고 ncclConnect 정보를 교환한다.
  4. channel.cc는 이 결과를 host/device 양쪽에서 접근 가능한 channel peer 구조체로 고정한다.

Collective 실행 흐름

초기화가 끝난 뒤 실제 데이터 경로는 API -> task -> plan -> kernel + proxy -> transport 순서로 진행된다.

ncclAllReduce / ncclSend / ncclRecv -> collectives.cc : ncclInfo 생성 -> group.cc : group batching, async job orchestration, preconnect -> enqueue.cc : argcheck, algorithm/protocol 결정, task queue 소비 -> enqueue.cc : channel partition, work batch 구성, proxy op 생성 -> ncclKernelPlan 생성 -> launch : kernel args + proxy queue submit -> device/common.h : blockIdx.x -> channelId -> device/all_reduce.h 등 : loop/chunk 단위 collective 알고리즘 수행 -> device/prims_*.h : slot 단위 send/recv/reduce/copy -> proxy.cc : host progress thread가 proxy op 소비 -> transport/net.cc / p2p.cc / shm.cc / coll_net.cc : 실제 isend/irecv/IPC/SHM progress -> net_ib/p2p.cc 또는 plugin backend : RDMA verbs / socket / offload backend 호출 -> completion / head-tail update / next slot reuse -> plan 완료

Figure 3와의 대응

host planner가 channel별 범위를 나누고, device algorithm 파일이 loop와 chunk를 돌며, prims_simple.h 계층이 slot pipeline을 구현한다.

실제 progress 주체

GPU kernel은 데이터 생산/소비와 ready publish를 하고, NIC 주입과 request completion test는 주로 host proxy가 담당한다.

이 구조 때문에 congestion control이나 receiver-driven admission 같은 실험은 kernel보다 먼저 proxy와 transport에서 보는 편이 맞다.

어디서부터 읽으면 좋은가

초기화 경로를 보고 싶다면

  1. init.cc
  2. bootstrap.cc
  3. graph/topo.cc -> paths.cc -> search.cc -> connect.cc
  4. channel.cc
  5. transport.cc

AllReduce 실행 경로를 보고 싶다면

  1. collectives.cc
  2. group.cc
  3. enqueue.cc
  4. device/all_reduce.h
  5. device/prims_simple.h
  6. transport/net.cc 또는 transport/p2p.cc

receiver-driven / CTS 실험을 하고 싶다면

  1. include/proxy.h
  2. transport/net.cc
  3. transport/net_ib/p2p.cc
  4. device/prims_simple.h
  5. enqueue.cc
처음부터 device/*만 보면 큰 그림을 놓치기 쉽다. NCCL은 kernel 라이브러리라기보다 planner와 proxy가 강하게 결합된 통신 런타임이기 때문에, host-side 상태와 transport 계층을 함께 봐야 구조가 맞게 잡힌다.
이 문서는 src/를 아키텍처 관점에서 재구성한 지도다. 다음 단계로는 AllReduce 하나를 골라 collectives.cc -> enqueue.cc -> device/all_reduce.h -> prims_simple.h -> transport/net.cc -> transport/net_ib/p2p.cc call chain을 순서대로 추적하면 된다.
