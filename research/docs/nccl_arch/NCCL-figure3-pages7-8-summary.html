Figure 3가 말하는 것

Figure 3는 Ring primitive 한 단계의 내부 동작보다, 큰 사용자 버퍼가 여러 communication channel로 나뉘고 각 channel이 자기 구간을 loop iteration으로 반복 처리하는 구조를 시각화한다.

8페이지의 핵심

분할된 channel 일은 CUDA block으로 매핑되고, 각 channel buffer는 다시 NCCL_STEPS개의 slot으로 쪼개져 미세 파이프라인을 만든다. 이 slot 파이프라인과 Ring step 순서는 다른 층의 개념이다.

Figure 3를 이해할 때 가장 중요한 기준은 channel = 큰 데이터 lane, loop = channel 구간 반복 처리, chunk = ring에서 도는 데이터 조각, slot = 실제 송수신 파이프라인 단위로 분리해서 보는 것이다.

Figure 3에서 말하는 Buffer가 실제로 무엇인가

Figure 3를 볼 때 가장 많이 생기는 오해는 channel buffer, send/recv buffer, sendMem/recvMem를 전부 같은 것으로 보는 것이다. 현재 NCCL 코드 기준으로 이 셋은 역할이 다르다.

User send/recv buffer

사용자가 collective 호출에 넘기는 실제 tensor 메모리다. Figure 3의 가장 바깥쪽 분할 대상은 기본적으로 이 버퍼다.

Channel / connection buffer

채널과 peer, protocol마다 붙는 staging buffer다. slot 기반 파이프라인은 보통 이 버퍼 위에서 돈다.

sendMem / recvMem

이 둘은 bulk payload buffer가 아니다. head, tail, connFifo 같은 메타데이터를 담는 제어용 메모리다.

직접 경로 예외

registered/direct path에서는 channel buffer를 우회해서 user buffer slice를 NIC source 또는 destination으로 직접 사용할 수 있다.

버퍼 종류 무엇을 담는가 기본 역할 대표 구조체
user sendbuff/recvbuff 사용자 tensor 자체 Figure 3의 channel 분할 원본 데이터 ncclTaskColl::sendbuff/recvbuff
channel/connection buffer slot 단위 payload 데이터 GPU, proxy, NIC 사이 staging 및 파이프라인 ncclConnInfo::buffs[]
sendMem head, pointer exchange 등 send 진행 상태 publish ncclSendMem
recvMem tail, connFifo[NCCL_STEPS] recv 진행 상태와 slot 메타데이터 ncclRecvMem

Figure 3와 연결해서 보면

  • Figure 3에서 channel이 처음 나누는 대상은 보통 user sendbuff/recvbuff다.
  • 각 channel의 loop와 chunk 실행 과정에서 실제 inter-node 송수신은 보통 channel/connection buffer의 slot을 통해 이뤄진다.
  • sendMem/recvMem는 데이터를 담는 곳이 아니라, 그 slot이 지금 사용 가능한지와 얼마나 진행됐는지를 나타내는 제어 정보다.
기본 staged path user sendbuff/recvbuff -> channel별 구간 분할 -> GPU kernel이 channel slot buffer에 write/read -> proxy가 slot ready 확인 -> NIC 전송 -> remote slot buffer -> remote GPU kernel -> user recvbuff 제어 정보는 별도 sendMem.head / recvMem.tail / connFifo[slot]
따라서 “channel buffer와 recv/send buffer는 같은가”라는 질문의 답은 기본 경로에서는 다르다가 맞다. 다만 direct/register 경로에서는 channel buffer를 우회할 수 있어서 둘이 사실상 직접 연결될 수 있다.

7페이지 정리: Iterative Execution of NCCL Collectives

  1. 사용자 입력 버퍼 전체를 active channel들에 먼저 분배한다.
  2. 각 channel은 자기 시작 위치와 길이를 가진다. 논문에서는 보통 workOffset, channelCount로 생각하면 된다.
  3. channel이 맡은 구간이 channel buffer보다 크면, 한 번에 처리하지 않고 여러 outer loop iteration으로 나눠서 실행한다.
  4. 각 loop iteration은 loopCount만큼의 element를 처리한다.
  5. 그 loop 내부에서는 다시 chunkCount 단위로 쪼개서 ring step이 수행된다.
여기서 Figure 3는 "채널별 데이터 배치와 반복 구조"를 보여주는 그림이다. 아직 이 단계에서는 recvReduceSend 같은 primitive sequence를 설명하는 것이 아니다.

Figure 3를 읽는 방법

예를 들어 channel이 2개라면 전체 데이터는 channel 0과 channel 1이 나눠 가진다. 각 channel은 자기 담당 구간을 기준으로 workOffset에서 시작한다. 그리고 자기 구간이 큰 경우에는 loopCount만큼 건너뛰면서 반복적으로 처리한다. 각 loop 안에서는 rank 수에 따라 여러 chunk가 생성되고, 그 chunk들이 ring을 따라 이동한다.

user buffer -> channel 0 담당 구간 -> channel 1 담당 구간 각 channel 내부 -> loop iteration 0 -> loop iteration 1 -> ... 각 loop 내부 -> chunk 0 -> chunk 1 -> ... -> ring step sequence 실행

현재 코드와의 대응

논문 용어 의미 현재 코드 대응
workOffset 해당 channel이 사용자 버퍼에서 시작하는 위치 partOffset 또는 kernel 지역변수 gridOffset
src/include/device.h, src/device/all_reduce.h
channelCount 해당 channel이 담당하는 전체 길이 partCount 또는 kernel 지역변수 channelCount
chunkCount loop 내부에서 ring이 한 번에 다루는 chunk 크기 kernel 지역변수 chunkCount
loopCount outer loop 1회가 처리하는 전체 element 수 Ring AllReduce에서는 nranks * chunkCount

숫자로 보는 Outer Loop / Chunk / Slot

예를 들어 nranks = 8, 어떤 channel이 맡은 구간이 channelCount = 256K elements, 그리고 kernel이 고른 chunkCount = 32K elements라고 하자. 그러면 Ring AllReduce에서는 loopCount = nranks * chunkCount = 256K가 되므로 outer loop는 1회만 돈다.

channelCount = 256K chunkCount = 32K nranks = 8 loopCount = 8 * 32K = 256K outer loop iteration 0 -> chunk 0 : [0, 32K) -> chunk 1 : [32K, 64K) -> chunk 2 : [64K, 96K) -> chunk 3 : [96K, 128K) -> chunk 4 : [128K, 160K) -> chunk 5 : [160K, 192K) -> chunk 6 : [192K, 224K) -> chunk 7 : [224K, 256K)

즉 outer loop 1회는 이 channel이 맡은 256K 전체를 처리하고, 그 내부에서 다시 nranks개의 chunk가 만들어져 ring step 순서로 이동한다. 이때 loopCount는 "outer loop 한 바퀴가 먹는 총 element 수"이고, chunkCount는 "그 안에서 rank별로 나뉘는 chunk 크기"다.

반대로 같은 nranks = 8, chunkCount = 32K인데 channelCount = 640K라면 loopCount는 그대로 256K이므로 outer loop는 3회 돈다.

iteration 0 -> elements [0, 256K) iteration 1 -> elements [256K, 512K) iteration 2 -> elements [512K, 640K)
여기서 chunk = slot으로 보면 안 된다. chunk는 ring 알고리즘이 다루는 데이터 단위이고, slot은 그 데이터가 실제로 흐를 때 사용하는 원형 buffer 위치다. 현재 코드는 step % NCCL_STEPS로 slot을 고른다.

따라서 chunk 하나가 slot 하나에 통째로 들어간다고 보면 틀리다. 더 정확히는 chunk가 내부적으로 slice와 step으로 나뉘어 pipeline 되고, 그 step들이 slot ring을 통해 흐른다. AllReduce는 CHUNKSTEPS와 SLICESTEPS를 따로 두므로, chunk와 slot은 같은 층위의 개념이 아니다.

Figure 3를 읽을 때의 계층은 channelCount -> outer loop(loopCount) -> chunk(chunkCount) -> slice/step -> slot 순서라고 보면 된다.

8페이지 정리: CUDA Hierarchy와 Slot Pipeline

8페이지는 7페이지의 분할 구조가 실제 CUDA 실행 모델로 어떻게 내려가는지를 설명한다. 핵심은 channel 하나를 대체로 block 하나가 담당한다는 점이다. 다만 channel이 SM과 1:1로 고정되는 것은 아니다. block이 어느 SM에서 실행될지는 GPU scheduler가 정한다.

CUDA block과 channel

kernel grid는 active channel 수만큼 block을 띄우고, 각 block이 자기 channel의 work를 처리한다. 현재 코드에서는 blockIdx.x가 channelMask를 통해 실제 channel ID로 변환된다.

slot 파이프라인

각 channel buffer는 다시 고정 개수의 slot으로 나뉜다. 기본값은 NCCL_STEPS = 8이며, 실제 primitive는 step % NCCL_STEPS 로 현재 slot을 선택한다.

왜 slot이 필요한가

  • GPU kernel이 slot 단위로 데이터를 생산하고 publish할 수 있다.
  • proxy나 peer는 ready 된 slot만 읽거나 보낼 수 있다.
  • slot이 여러 개 있으면 한 채널 안에서도 생산, 전송, 소비가 겹치며 진행된다.
계층 무엇을 나누는가 역할 대표 코드
Channel 사용자 전체 버퍼 큰 데이터 lane 분할 ncclCollCbdPart()
Loop iteration channel 담당 구간 channel 구간을 여러 번 반복 처리 for (elemOffset += loopCount)
Chunk loop 내부 데이터 ring step이 도는 조각 chunkCount
Slot channel buffer 송수신 파이프라인, readiness, 동기화 step % NCCL_STEPS
많이 헷갈리는 지점은 slot과 loop를 같은 것으로 보는 것이다. loop는 알고리즘이 처리하는 데이터 구간의 반복이고, slot은 그 데이터를 실제로 흘리는 버퍼 파이프라인이다.

Ring AllReduce step 순서와 Figure 3의 관계

8페이지는 Ring AllReduce가 각 loop에서 어떤 step sequence를 갖는지도 같이 설명한다. 이 부분은 Figure 3보다 한 단계 더 아래의 primitive 수준이다. 즉 Figure 3는 "데이터가 어떻게 쪼개지나"를 보여주고, 아래 표는 "쪼개진 chunk가 loop 안에서 어떤 순서로 처리되나"를 보여준다.

단계 논문 표현 의미 현재 Ring AllReduce 코드
step 0 send 첫 chunk를 다음 rank로 보냄 directSend
step 1 ... k-2 recvReduceSend 받은 chunk를 로컬 값과 reduce 후 다음 rank로 전달 directRecvReduceDirectSend
step k-1 recvReduceCopySend 최종 reduction 결과를 만들고 로컬 결과 버퍼에 복사한 뒤 전달 directRecvReduceCopyDirectSend
step k ... 2k-3 recvCopySend 완성된 결과를 ring을 따라 퍼뜨림 directRecvCopyDirectSend
step 2k-2 recv 마지막 결과를 받아 최종 위치에 둠 directRecv
따라서 Figure 3와 step table을 섞어 보면 안 된다. Figure 3는 분할 구조, step table은 분할된 chunk의 실행 순서다.

현재 코드 기준으로 다시 해석한 실행 흐름

host planner -> channelLo/channelHi, countLo/countMid/countHi 계산 -> channel별 chunk 크기 결정 device kernel 진입 -> blockIdx.x 를 channelId 로 변환 -> ncclCollCbdPart() 로 gridOffset, channelCount, chunkCount 계산 -> outer loop: elemOffset += loopCount -> 각 loop에서 여러 chunk에 대해 ring step 수행 -> 각 step은 slot(step % NCCL_STEPS)을 통해 송수신 -> slot size publish 후 다음 peer/proxy가 소비

코드 포인트

주제 파일 설명
channel 분할 src/enqueue.cc channelLo/channelHi, countLo/countMid/countHi, chunkGrains* 계산
channel-local 해석 src/include/device.h ncclCollCbdPart()가 channel별 offset, count, chunk를 결정
block to channel src/device/common.h blockIdx.x를 실제 channel ID로 매핑
Ring loop src/device/all_reduce.h loopCount = nranks * chunkCount 기반 outer loop와 ring steps
slot pipeline src/device/prims_simple.h connFifo[step % NCCL_STEPS]와 slot size publish

이 구간에서 꼭 잡아야 하는 오해 3개

  1. channel은 SM이 아니다. 보통 channel work를 CUDA block 하나가 담당할 뿐이고, 어떤 SM에서 실행될지는 런타임이 정한다.
  2. loop와 slot은 다르다. loop는 데이터 구간 반복, slot은 통신 버퍼의 파이프라인 단위다.
  3. Figure 3는 primitive가 아니라 스케줄링 그림이다. recvReduceSend 같은 세부 연산은 그 다음 단계 설명이다.
