1. 현재 NCCL 데이터 경로 핵심 요약

기본 NCCL 구현은 user buffer와 channel/connection buffer를 함께 사용한다. 하지만 채널마다 별도의 persistent compute buffer를 하나씩 두는 구조는 아니다. 로컬 원본 데이터는 기본적으로 사용자가 넘긴 sendbuff/recvbuff에 있고, channel은 그 데이터를 channel별 오프셋으로 논리 분할해서 처리한다.

무엇이 실제로 존재하나

  • channel buffer는 실제로 존재한다.
  • 정확히는 channel x peer x send/recv x protocol 단위 connector buffer다.
  • 핵심 구조는 ncclConnInfo::buffs[], connFifo, head/tail다.

무엇이 채널별로 따로 없나

  • 채널별 독립 persistent compute buffer는 기본 구조가 아니다.
  • compute 대상 로컬 데이터는 보통 user sendbuff/recvbuff에 있다.
  • 채널은 이 user buffer를 channel별 offset으로 slice해서 본다.
질문 현재 NCCL 구현 기준 답 주요 위치
channel buffer가 실제로 존재하나 존재한다. 단일 버퍼가 아니라 connector 단위의 buffs[]와 connFifo로 구성된다. src/include/device.h, src/include/comm.h
compute 전 데이터는 어디 있나 로컬 operand는 user sendbuff/recvbuff, remote operand는 보통 incoming slot buffer에 있다. src/device/common.h, src/device/prims_simple.h
compute 후 channel buffer로 가나 기본 경로에서는 맞다. 결과가 outgoing slot에 기록되고 proxy/NIC가 그 slot을 소비한다. src/device/prims_simple.h, src/transport/net.cc
slot 단위로 NIC에 나가나 inter-node NET 경로 기준으로 맞다. step % NCCL_STEPS 슬롯이 전송 단위가 된다. src/include/device.h, src/transport/net.cc

1-1. 왜 “channel buffer”가 아니라 사실상 “connector buffer”인가

앞에서 편의상 channel buffer라고 불렀지만, 코드 구조상 더 정확한 표현은 channel 안에 있는 peer-direction connector의 buffer다. 즉 하나의 channel에 단일 payload buffer가 붙는 것이 아니라, channel -> peer -> send/recv connector -> conn 계층 아래에 버퍼와 메타데이터가 달린다.

struct ncclConnInfo { char* buffs[NCCL_NUM_PROTOCOLS]; void* mhandles[NCCL_NUM_PROTOCOLS]; uint64_t* tail; uint64_t* head; int stepSize; struct ncclConnFifo* connFifo; ... }; struct ncclConnector { struct ncclProxyConnector proxyConn; struct ncclTransportComm* transportComm; void* transportResources; struct ncclConnInfo conn; }; #define NCCL_MAX_CONNS 2 struct ncclChannelPeer { struct ncclConnector send[NCCL_MAX_CONNS]; struct ncclConnector recv[NCCL_MAX_CONNS]; };

따라서 어떤 rank가 channel c에서 peer p와 통신할 때 GPU와 proxy가 실제로 보는 상태는 대략 다음 중 하나다.

  • comm->channels[c].peers[p]->send[0].conn
  • comm->channels[c].peers[p]->recv[0].conn
  • 특수한 P2P round 또는 추가 연결이 있으면 send[1], recv[1]도 사용 가능
논리 계층 channel c -> peer p -> send[connIndex] 또는 recv[connIndex] -> connector.conn -> buffs[LL], buffs[LL128], buffs[Simple] -> connFifo[NCCL_STEPS] -> head / tail / stepSize / mhandles 즉 "channel buffer"라는 말은 실제로는 "channel 안의 특정 peer-direction connector가 가진 protocol buffer + slot metadata" 를 줄여 부르는 표현에 가깝다.
차원 실제 코드 구조 왜 필요한가
channel comm->channels[channelId] 데이터를 병렬 lane으로 분할하기 위해
peer channel.peers[peer] 각 channel이 서로 다른 rank와 독립 연결을 가져야 하기 때문
direction send[], recv[] 송신과 수신의 credit, slot lifecycle, transport 상태가 다르기 때문
connection index [0], [1] P2P round 분리나 특수 경로를 위한 추가 connection slot
protocol buffs[NCCL_PROTO_LL/LL128/SIMPLE] 프로토콜마다 payload layout과 step granularity가 다르기 때문
따라서 “channel별로 buffer가 하나 있다”는 말은 개념적으로는 맞지만, 코드 레벨에서는 너무 거칠다. 실제 payload와 메타데이터는 ncclConnector::conn에 매달려 있고, 그 connector가 channel/peer/direction 단위로 복제된다.

1-2. ncclConnInfo::buffs[], connFifo, head/tail는 정확히 무엇인가

ncclConnInfo는 GPU kernel과 proxy가 공유하는 “연결의 실행 상태”다. 이 안에는 payload buffer base, per-slot metadata, credit pointer, protocol별 memory handle이 같이 들어 있다.

struct ncclConnFifo { int mode; int offset; ssize_t size; void* ptr; }; struct ncclSendMem { uint64_t head; void* ptrExchange; uint64_t redOpArgExchange[2]; int offsFifo[NCCL_STEPS]; }; struct ncclRecvMem { uint64_t tail; struct ncclConnFifo connFifo[NCCL_STEPS]; int flush; };
필드 의미 중요 포인트
buffs[] protocol별 payload buffer의 base pointer LL, LL128, Simple 각각 별도 base를 가진다.
mhandles[] protocol별 memory registration handle registered/direct NIC 경로에서 중요하다.
stepSize Simple protocol에서 slot 하나의 크기 보통 buffSize[SIMPLE] / NCCL_STEPS로 계산된다.
connFifo GPU와 proxy가 주고받는 per-slot 메타데이터 배열 payload 그 자체가 아니라 slot의 주소/크기/모드를 전달하는 control 구조다.
tail producer frontier 새 데이터가 어느 step까지 준비되었는지 또는 수신 완료되었는지를 publish한다.
head consumer frontier 어느 step까지 소비가 끝나 slot을 재사용해도 되는지를 publish한다.
step 이 connection의 현재 step cursor 다음 collective 또는 다음 sub-step에서 이어서 사용된다.

buffs[]: 실제 payload 저장소

buffs[]는 protocol별 payload base pointer다. Simple protocol에서는 실제 slot address가 보통 아래처럼 계산된다.

connStepSize = conn->stepSize / sizeof(T); connEltsFifo = (T*)conn->buffs[NCCL_PROTO_SIMPLE]; // 기본 모드 ptr = connEltsFifo + (step % NCCL_STEPS) * connStepSize; // shared-buffer 모드 if (connFifo[slot].mode == NCCL_MODE_OFFSET) { ptr = connEltsFifo + connFifo[slot].offset / sizeof(T); }
  • NCCL_MODE_NORMAL: base + slot * stepSize 형태의 고정 slot 배치
  • NCCL_MODE_OFFSET: proxy가 slot마다 offset을 써 주고 GPU가 그 offset을 따라감
  • NCCL_MODE_PTR: pointer 기반 모드. 일부 direct path나 특수 경로를 위해 예약된 형태
즉 buffs[]는 “채널의 데이터가 저장되는 큰 메모리 영역의 시작점”이고, connFifo[slot]는 “이번 slot이 그 큰 영역의 어디를 써야 하는가”를 조정하는 메타데이터다.

connFifo: per-slot metadata channel

connFifo[NCCL_STEPS]는 payload buffer가 아니라, 각 slot에 대해 GPU와 proxy가 서로 읽고 쓰는 메타데이터 채널이다.

// GPU가 send slot 생산 완료를 publish connFifo[step % NCCL_STEPS].size = dstSize * sizeof(T); // proxy가 send 가능 여부를 확인 if (connFifo[buffSlot].size != -1 && *recvTail > tail) { buff = shared ? localBuff + connFifo[buffSlot].offset : localBuff + buffSlot * stepSize; ncclNet->isend(...); } // 전송 완료 후 proxy가 slot 재활용 표시 connFifo[buffSlot].size = -1;
필드 누가 쓰나 언제 쓰나 주된 의미
mode proxy/connect 단계 연결 생성 시 slot 주소 계산 방식을 선택
offset proxy shared buffer path에서 slot post 시 buffs[] base 안에서의 실제 slot 위치
size GPU / proxy GPU가 생산 완료 시 기록, proxy가 완료 후 reset slot ready 여부와 payload 길이
ptr 특수 경로 필요 시 직접 pointer 기반 mode 지원

head/tail: byte offset가 아니라 step frontier

head와 tail은 단순 포인터가 아니라, 어느 step까지 생산 또는 소비가 완료되었는지를 나타내는 진행 카운터다. slot 재사용 가능 여부는 결국 이 두 frontier 차이로 정해진다.

// send connector wiring (net.cc) send->conn.head = &sendMem->head; send->conn.tail = &recvMem->tail; send->conn.connFifo = recvMem->connFifo; // recv connector wiring (net.cc) recv->conn.head = &sendMem->head; recv->conn.tail = &recvMem->tail; recv->conn.connFifo = recvMem->connFifo;

이름이 헷갈리지만 의미는 간단하다.

  • tail: producer가 “여기까지는 새 데이터가 준비됐다”라고 publish하는 frontier
  • head: consumer가 “여기까지는 소비했으니 이전 slot은 재사용 가능하다”라고 돌려주는 frontier
send path에서의 해석 GPU가 slot을 채움 -> connFifo[slot].size publish -> tail frontier가 앞으로 감 proxy가 network send 완료 -> connFifo[slot].size = -1 -> head frontier를 앞으로 밀어 credit 반환 recv path에서의 해석 proxy가 network receive 완료 -> tail frontier를 앞으로 밀어 "GPU가 읽어도 됨" publish GPU가 slot을 읽고 reduce/copy 완료 -> head frontier를 앞으로 밀어 "이전 slot 재사용 가능" 반환
실무적으로는 head/tail를 “큐 포인터”라고만 보면 부족하다. 더 정확히는 producer와 consumer 사이에서 slot credit를 주고받는 step-level credit frontier로 이해하는 편이 맞다.

connect 단계에서 실제로 어떻게 wiring되나

NET transport의 sendConnect() / recvConnect()를 보면, 연결 생성 시점에 payload base와 메타데이터 포인터가 모두 conn에 박힌다.

// sendConnect() send->conn.head = ...sendMem->head; send->conn.tail = ...recvMem->tail; send->conn.stepSize = buffSize[SIMPLE] / NCCL_STEPS; send->conn.connFifo = recvMem->connFifo; for (int p = 0; p < NCCL_NUM_PROTOCOLS; p++) send->conn.buffs[p] = ...; // recvConnect() recv->conn.head = ...sendMem->head; recv->conn.tail = ...recvMem->tail; recv->conn.stepSize = buffSize[SIMPLE] / NCCL_STEPS; recv->conn.connFifo = recvMem->connFifo; for (int p = 0; p < NCCL_NUM_PROTOCOLS; p++) recv->conn.buffs[p] = ...;

즉 GPU kernel이 보는 모든 핵심 정보는 launch 시점에 따로 계산되는 것이 아니라, 이미 connect 단계에서 connector.conn 안에 wiring되어 있다. kernel은 이후 conn->buffs[], conn->connFifo, conn->head, conn->tail만 따라가면 된다.

로컬 data와 remote data의 위치

  • 로컬 data: user가 넘긴 sendbuff/recvbuff
  • remote에서 들어온 data: 일반적으로 connEltsFifo + (step % NCCL_STEPS) * connStepSize
  • 예외: direct/registered path에서는 slot staging 대신 direct pointer 또는 user buffer를 바로 사용할 수 있음
기본 경로 user buffer slice + incoming slot -> GPU reduce/copy -> outgoing slot 또는 final recvbuff -> proxy가 slot ready 확인 -> NIC / net transport 전송 예외 경로 user buffer / direct pointer -> 중간 slot 일부 또는 전부 우회 -> proxy 또는 NIC가 직접 registered buffer 사용

2. slot과 proxy가 실제로 어떻게 맞물리나

NCCL은 내부적으로 NCCL_STEPS 크기의 원형 slot ring을 사용한다. GPU kernel은 slot에 쓰고, proxy는 그 slot이 준비됐는지 확인한 뒤 network 전송을 건다. recv 측도 반대로 slot이나 direct buffer에 받아서 GPU가 소비하게 만든다.

GPU 측 역할

  • step % NCCL_STEPS로 현재 slot 선택
  • incoming src pointer와 outgoing dst pointer 결정
  • reduce/copy 후 connFifo[slot].size publish

Proxy 측 역할

  • slot size와 head/tail을 보고 전송 가능 여부 판단
  • ready slot이면 ncclNet->isend() 호출
  • recv 완료 후 GPU가 볼 수 있게 recvTail를 진전
AllReduce Ring 관점의 단순 call chain GPU kernel 1 step -> local outgoing slot 채움 -> connFifo[slot].size 기록 -> send proxy가 slot ready 감지 -> ncclNet->isend(...) -> remote recv proxy가 irecv/complete -> remote recvTail publish -> remote GPU kernel이 incoming slot 소비 -> local compute/user buffer에 reduce/copy
direct/register 경로에서는 위 흐름의 일부가 바뀐다. 특히 registered path는 proxy가 ringAlgo->getNextSendAddr() / getNextRecvAddr()를 통해 user buffer를 직접 NIC에 넘길 수 있다.

2-1. 시간축으로 보면 왜 이게 pipeline인가

헷갈리는 지점은 이것이다. NCCL은 slot이 꽉 차면 분명히 기다린다. 그런데도 pipeline이라고 부르는 이유는, 모든 slot이 동시에 같은 단계에 있지 않기 때문이다. 어떤 slot은 GPU가 쓰고 있고, 다른 slot은 proxy가 NIC로 보내고 있고, 또 다른 slot은 remote에서 GPU가 읽고 있을 수 있다.

즉 NCCL의 pipeline은 “wait가 없는 pipeline”이 아니라 깊이가 NCCL_STEPS인 bounded pipeline이다.

head와 tail를 먼저 이렇게 보면 된다

  • tail: producer가 “여기까지는 새 데이터가 준비됐다”라고 민 frontier
  • head: consumer가 “여기까지는 소비 끝났고 이전 slot은 재사용 가능하다”라고 돌려준 frontier
  • 아직 처리 중인 step 구간은 개념적으로 [head, tail)다.
  • outstanding step 수는 tail - head로 볼 수 있다.
핵심 해석 empty : tail == head in-flight : 0 < tail - head < NCCL_STEPS full : tail - head == NCCL_STEPS slot 선택은 항상 slot = step % NCCL_STEPS producer는 다른 free slot을 "검색"하지 않는다. 자기 차례 step의 slot을 쓰고, 그 slot이 아직 재사용 불가면 head가 전진할 때까지 기다린다.

send connector 관점 시간축 예시

아래 표는 NCCL_STEPS = 4인 send path를 단순화한 예시다. 여기서는 GPU가 producer, send proxy + NIC가 consumer다.

시간 head tail slot 0 slot 1 slot 2 slot 3 설명
t0 0 0 free free free free 아직 생산된 step이 없다. pipeline이 비어 있다.
t1 0 1 ready(step0) free free free GPU가 step0을 slot0에 썼다. 이제 outstanding 구간은 [0,1).
t2 0 2 sending(step0) ready(step1) free free proxy는 slot0을 NIC로 보내고, GPU는 동시에 slot1에 step1을 쓸 수 있다. 이것이 overlap이다.
t3 1 3 free sending(step1) ready(step2) free proxy가 step0 소비를 끝내 head=1을 반환했다. slot0은 다시 재사용 가능하다.
t4 1 4 free sending(step1) ready(step2) ready(step3) 여전히 pipeline 안에 여러 step이 겹쳐 있다. outstanding은 [1,4).
t5 1 5 ready(step4) sending(step1) ready(step2) ready(step3) GPU는 slot0을 step4로 재사용했다. step 번호는 커졌지만 slot은 modulo로 재사용된다.
t6 1 5 ready(step4) sending(step1) ready(step2) ready(step3) 이 시점에서 outstanding은 tail - head = 4. ring depth가 가득 찼으므로 GPU는 다음 step5를 못 쓰고 대기한다.
t7 2 5 ready(step4) free sending(step2) ready(step3) proxy가 step1 소비를 끝내 head=2가 되면 다시 빈 자리가 생기고 pipeline이 전진한다.
위 표에서 중요한 건 t2~t5다. 한쪽에서는 GPU가 새 slot을 채우고, 다른쪽에서는 proxy/NIC가 이전 slot을 보내고 있다. 즉 대기가 없어서 pipeline인 것이 아니라, 여러 step이 서로 다른 slot에서 동시에 진행되기 때문에 pipeline이다.

recv connector는 역할만 뒤집히면 된다

recv path에서는 의미가 반대로 읽힌다.

  • producer: recv proxy + NIC
  • consumer: GPU kernel
  • tail: network에서 도착한 step frontier
  • head: GPU가 소비 완료하고 돌려준 credit frontier
recv path 해석 proxy/NIC가 step k를 slot에 채움 -> tail 증가 GPU는 tail이 자기 차례 step까지 오면 slot을 읽음 -> reduce/copy 완료 -> head 증가 즉 recv path도 동일하게 [head, tail) = 도착했지만 아직 GPU가 소비하지 않은 구간 으로 읽으면 된다.

결국 wait는 언제 생기나

조건 누가 기다리나 의미
tail == head consumer 아직 받을/읽을 데이터가 없어서 기다림
tail - head == NCCL_STEPS producer ring depth가 가득 차서 다음 slot을 재사용할 수 없어 기다림
0 < tail - head < NCCL_STEPS 둘 다 계속 진행 가능 파이프라인이 정상적으로 겹쳐서 흐르는 구간
따라서 NCCL의 slot pipeline을 이해할 때는 head/tail를 “각 소비되어야 할 구간, 소비된 구간”의 경계로 보면 된다. 더 정확히는 미소비 구간의 양이 tail - head이고, 이 값이 0이면 consumer가, NCCL_STEPS면 producer가 막힌다.

3. Receiver-Driven Traffic Admission의 정확한 의미

논문 5.2.2의 핵심은 sender가 “데이터가 준비됐으니 바로 보낸다”가 아니라, receiver가 “내가 받을 slot이 하나 비었으니 이제 보내도 된다”라고 허가한 경우에만 네트워크 주입을 허용하는 것이다. 즉 congestion control을 transport 레벨 rate control보다 더 위인 collective library slot lifecycle에 연결하는 방식이다.

핵심 문장으로 줄이면, receiver free-slot 기반 credit control이다.

왜 이게 효과가 있나

  • receiver가 느려지면 slot recycle이 늦어진다.
  • slot recycle이 늦어지면 새 CTS가 나오지 않는다.
  • 새 CTS가 없으면 sender proxy가 추가 전송을 못 한다.
  • 즉 in-flight traffic 상한이 receiver의 실제 수용 속도와 slot 수에 의해 묶인다.
sender-driven 기본 NCCL GPU slot ready -> proxy -> isend -> network receiver-driven NCCL receiver free slot -> CTS 송신 sender가 CTS 수신 GPU slot ready && matching CTS 있음 -> proxy -> isend / RDMA write -> network

3-1. slot 기반 pipeline의 실제 lifecycle

중요한 점은 현재 NCCL이 slot 상태를 단일 enum 하나로 저장하지 않는다는 것이다. 실제 상태는 connFifo[slot].size, head/tail, proxy의 posted/received/transmitted/done, request pointer 존재 여부가 합쳐져서 암묵적으로 표현된다.

즉 “slot status”는 개념적으로는 분명하지만, 코드상으로는 하나의 status 필드가 아니라 여러 메타데이터 조합으로 판단해야 한다.

send 측 slot lifecycle

1. proxy가 다음 step의 slot을 GPU에 노출 -> shared path면 connFifo[slot].offset 설정 -> posted 증가 2. GPU kernel이 slot pointer를 계산 -> connEltsFifo + (step % NCCL_STEPS) * connStepSize -> 또는 direct/register path면 directBuff / user buffer 3. GPU가 slot에 데이터 기록 -> reduce/copy 수행 -> connFifo[slot].size = bytes publish -> step/head 진행 4. send proxy가 ready 확인 -> connFifo[slot].size != -1 -> recvTail/head window 조건 만족 -> ncclNet->isend(...) 5. network send 완료 -> connFifo[slot].size = -1 로 reset -> sendHead 진행 -> slot 재사용 가능

recv 측 slot lifecycle

1. recv proxy가 target buffer를 선택 -> 기본 path면 localBuff + slot * stepSize -> shared path면 offset 기반 shared buffer -> reg/direct path면 ringAlgo->getNextRecvAddr()로 user buffer slice 2. recv proxy가 ncclNet->irecv(...) post -> request 저장 -> posted 증가 3. network 수신 완료 -> size 수집 -> 필요시 flush -> received 증가 4. recv proxy가 recvTail publish -> GPU가 이 slot을 소비 가능 -> transmitted 증가 5. GPU kernel이 slot을 읽어 reduce/copy -> sendHead/head를 통해 소비 완료를 간접 publish -> recv proxy의 done 증가 -> slot 재사용 가능

개념적 status와 실제 판단 신호

개념적 status 의미 실제 코드에서 주로 보는 신호
FREE 아직 아무 것도 담기지 않았고 재사용 가능 connFifo[slot].size == -1, window 여유 존재
POSTED_TO_GPU GPU가 이 slot을 사용하도록 proxy가 준비 완료 posted > transmitted 또는 offset/head publish 완료
GPU_FILLING GPU가 slot에 write / reduce 중 명시적 bit 없음, connFifo.size가 아직 final 값이 아님
GPU_READY send slot 데이터가 proxy가 보낼 준비 완료 connFifo[slot].size != -1
NET_INFLIGHT proxy가 이미 network request를 post함 requests[slot] != NULL, transmitted > done
NET_FILLED recv target에 데이터 도착 완료 recv-side test() 완료, received 증가
GPU_CONSUMABLE recv slot을 GPU가 읽을 수 있음 recvTail publish 완료
RECYCLED GPU가 소비를 끝내 다시 free 상태로 돌아감 sendHead/head 진전, done 증가, 다음 reuse 가능

slot pipeline이 생기는 이유

  • slot 0은 GPU가 채우는 중이고, slot 1은 proxy가 NIC에 보내고, slot 2는 remote에서 GPU가 읽는 식으로 단계가 겹칠 수 있다.
  • 즉 한 channel 안에서도 생산, 전송, 소비가 동시 진행된다.
  • 이 중첩이 바로 NCCL의 slot 기반 pipeline이다.
시간축 예시 t0: GPU fills slot 0 t1: proxy sends slot 0, GPU fills slot 1 t2: remote recv completes slot 0, local proxy sends slot 1, GPU fills slot 2 t3: remote GPU consumes slot 0, local/remote 양쪽에서 다음 slot들 진행

4. NCCL core 층에서 구현한다면 어디를 고쳐야 하나

이 메커니즘은 kernel 수식 자체를 바꾸는 문제가 아니라, channel slot을 network에 올리는 시점을 gate하는 문제다. 그래서 가장 자연스러운 삽입 지점은 CUDA kernel보다 proxy + net transport 계층이다.

계층 현재 역할 receiver-driven에서 추가할 것
GPU kernel slot에 쓰고 publish 가능하면 변경 최소화. 기존 slot publish 유지
send proxy slot ready면 isend() CTS/credit 없으면 전송 금지
recv proxy irecv(), flush, GPU tail publish slot recycle 시 새 CTS 발급
control plane 거의 없음 고우선순위 CTS 송수신 경로 추가

구체적 수정 포인트

  • src/include/proxy.h: proxy sub-arg에 credit/CTS 상태 배열 추가
  • src/transport/net.cc의 sendProxyProgress(): slot ready 외에 credit 보유 조건 추가
  • src/transport/net.cc의 recvProxyProgress(): slot recycle 완료 시 새 CTS 송신
  • 필요시 net plugin 또는 별도 control QP: CTS(slot_id, addr, rkey, size, seq) 전달
app 상단에서만 구현하면 collective 호출 단위 gating은 가능하지만, NCCL 내부의 channel/slot 단위 admission은 제어할 수 없다. 논문 5.2.2 수준에 가장 가깝게 가려면 core 또는 transport/plugin 수정이 필요하다.

5. 필요한 상태 머신

Sender slot 상태

EMPTY -> GPU_FILLED -> CTS_GRANTED -> NET_INFLIGHT -> EMPTY

Receiver slot 상태

FREE -> CTS_SENT -> FILLED_BY_NET -> GPU_CONSUMING -> FREE

CTS에 실려야 할 최소 정보

  • peer/channel/slot 식별자
  • remote address 및 rkey 또는 send permission에 해당하는 handle
  • 허용 byte 수 또는 slice 수
  • seq/epoch 값
현재 IB transport의 기본 CTS도 실제로는 이와 유사한 정보를 담는다. receiver는 addr, rkeys[], size, tag, idx를 채워 sender 쪽 CTS FIFO로 보낸다. 다만 여기의 addr는 항상 channel slot 주소인 것은 아니고, staged path에서는 slot buffer 주소, direct/register path에서는 user buffer slice 주소가 될 수 있다.
slot_id만으로는 stale CTS를 막기 어렵다. 같은 slot이 재사용되므로 반드시 seq/epoch를 같이 들고 가야 한다.

6. 의사코드

sendProxyProgress 쪽 개념

for each sub: slot = (base + transmitted) % NCCL_STEPS if local slot is not ready: continue credit = ctsQueue.lookup(peer, channelId, slot) if credit is missing: continue buff = local slot buffer or registered user buffer size = connFifo[slot].size post_network_send(buff, size, credit.remote_addr, credit.rkey) mark slot as inflight consume credit(slot, seq)

recvProxyProgress 쪽 개념

for each sub: if free slot exists and no outstanding CTS for that slot: send_cts(peer, channelId, slot, remote_addr, rkey, size, seq) mark slot as CTS_SENT if network write/recv completed into slot: mark slot as FILLED_BY_NET publish recvTail so GPU can consume if GPU finished consuming slot: recycle slot bump seq send next CTS

7. 구현 시 튜닝 포인트

  • 채널 수: 많을수록 병렬성은 늘지만 GPU thread/resource contention도 커진다.
  • slot 크기: 너무 크면 in-flight burst가 커지고, 너무 작으면 CTS/control overhead가 커진다.
  • credit depth: slot 1개씩 줄지, 여러 slot window를 줄지 결정해야 한다.
  • CTS 우선순위: data traffic에 묻히면 receiver-driven이 오히려 stall을 만든다. 별도 high-priority queue가 유리하다.
  • direct/registered path: slot staging을 우회하는 경로도 동일한 CTS gate를 공유해야 한다.

8. 최종 정리

  • 현재 NCCL은 user buffer와 channel slot buffer를 함께 쓰며, 채널별 persistent compute buffer를 따로 두지는 않는다.
  • 기본 경로는 user buffer slice + incoming slot -> compute -> outgoing slot -> proxy -> NIC다.
  • slot은 실제로 step % NCCL_STEPS로 굴러가며, inter-node NET 경로에서 proxy/NIC 전송 단위가 된다.
  • receiver-driven admission은 sender의 network injection을 receiver free-slot 기반 CTS로 gate하는 방식이다.
  • 이를 NCCL답게 구현하려면 kernel보다 src/transport/net.cc와 src/include/proxy.h 중심으로 넣는 것이 맞다.
정리 대상 파일: src/include/device.h, src/include/comm.h, src/device/common.h, src/device/prims_simple.h, src/include/collectives.h, src/transport/net.cc, src/include/proxy.h
