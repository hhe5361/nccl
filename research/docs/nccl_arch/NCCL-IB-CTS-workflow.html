NCCL IB Transport

CTS 발급 Workflow (함수 단위 Call Chain)

질문 포인트였던 “receiver가 conn.buffs와 connFifo를 직접 스캔해서 CTS를 보내는가?” 를 코드 실행 경로 기준으로 정리했다.

관점: proxy + transport 분리 대상: src/transport/net.cc, src/transport/net_ib/p2p.cc 핵심: CTS는 “recv target ready” 신호

1. 한 줄 결론

CTS 발급의 직접 트리거는 receiver proxy가 irecv를 post한 시점이다. 즉 receiver가 slot을 “직접 스캔해서” CTS를 보내는 구조라기보다, recvProxyProgress()의 step/window 상태(posted/done/maxDepth)로 recv target을 결정하고, 그 target 정보를 IB plugin이 CTS로 포장해 sender에 쓰는 구조다.

recvProxyProgress() in net.cc -> next recv step을 열 수 있는지 판단(posted < done + maxDepth) -> buffSlot 계산, ptr/size/mhandle/tag 준비 -> ncclNet->irecv(...) -> ncclIbIrecv() in net_ib/p2p.cc -> local CTS element(addr/rkey/size/tag/idx) 작성 -> ncclIbPostFifo()로 sender ctsFifo에 RDMA write (CTS 발급) sendProxyProgress() in net.cc -> local payload ready 확인 -> ncclNet->isend(...) -> ncclIbIsend() in net_ib/p2p.cc -> expected idx CTS 도착 확인 -> 도착 시에만 RDMA send/write 진행

2. 함수 단위 Call Chain

2.1 Receiver 측: recv target 결정

단계 함수 핵심 판단/동작
R1 recvProxyProgress() (net.cc) sub->posted < sub->done + maxDepth일 때만 다음 recv step을 열어 backpressure를 건다.
R2 recvProxyProgress() buffSlot = (sub->base + sub->posted) % NCCL_STEPS로 slot을 고르고, ptrs[]/sizes[]/mhandles[]/tags[]를 구성한다.
R3 proxyState->ncclNet->irecv(...) transport plugin(IB 포함)으로 recv target을 전달한다.

2.2 IB plugin: CTS 생성 및 발급

단계 함수 핵심 판단/동작
I1 ncclIbIrecv() (net_ib/p2p.cc) recv request 생성 후 slot = fifoHead % NET_IB_MAX_REQUESTS를 잡는다.
I2 ncclIbIrecv() localElem[i]에 addr/rkeys/size/tag/idx를 채운다. 여기서 addr는 proxy가 넘긴 recv target(data[i])이다.
I3 ncclIbPostFifo() receiver가 sender의 ctsFifo 원격 주소(remCtsFifo.addr)로 RDMA write를 post한다. 이것이 CTS 발급이다.

2.3 Sender 측: CTS 소비 후 전송

단계 함수 핵심 판단/동작
S1 sendProxyProgress() (net.cc) GPU가 payload를 준비했는지 connFifo[buffSlot].size, recvMem->tail 등으로 확인한다.
S2 proxyState->ncclNet->isend(...) transport plugin으로 전송 시도.
S3 ncclIbIsend() (net_ib/p2p.cc) slots = comm->ctsFifo[slot], expected idx를 확인. slots[0].idx != idx면 전송하지 않고 반환한다.
S4 ncclIbMultiSend() matching CTS가 있으면 RDMA send/write를 실제 QP에 post한다.

3. 질문 포인트에 대한 정확한 답

Q1. receiver가 conn.buffs를 직접 스캔하나?

직접 스캔 기반이라기보다, recvProxyProgress()의 step/window 상태에서 다음 recv를 열고 그때 target pointer를 결정한다.

Q2. connFifo를 보고 CTS를 보내나?

간접적으로는 맞다. proxy가 slot/target 계산 시 connFifo를 사용한다. 하지만 CTS 발급 자체는 ncclIbIrecv -> ncclIbPostFifo에서 수행된다.

Q3. CTS payload는 무엇인가?

“빈 slot 개수”가 아니라 addr/rkey/size/tag/idx다. sender는 이 정보를 받아 해당 remote target으로 write한다.

Q4. sender는 무엇을 기다리나?

local payload ready + matching CTS 둘 다 필요하다. CTS가 늦으면 local data가 준비돼도 ncclIbIsend()에서 막힌다.

따라서 “transport가 ncclConnInfo::buffs[]와 connFifo를 직접 순회해서 빈칸을 찾고 CTS를 만든다”라고 이해하면 과도하게 단순화된다. 실제 구조는 proxy가 recv target을 열고, IB plugin은 그 target을 CTS로 전달하는 2단계다.

4. 코드 포인트(읽기 순서)

  1. src/transport/net.cc의 recvProxyProgress()에서 posted/done/maxDepth와 irecv 호출 흐름 확인
  2. src/transport/net_ib/p2p.cc의 ncclIbIrecv()에서 localElem.addr/rkeys/size/tag/idx 채우는 부분 확인
  3. src/transport/net_ib/p2p.cc의 ncclIbPostFifo()에서 sender ctsFifo로 RDMA write 하는 부분 확인
  4. src/transport/net_ib/p2p.cc의 ncclIbIsend()에서 slots[0].idx == expected idx 검사 확인
  5. src/transport/net.cc의 sendProxyProgress()에서 local payload ready 판정과 isend 호출 연결 확인
이 순서대로 보면 CTS가 “빈 버퍼 스캔 패킷”이 아니라 “posted recv target 기반 admission 토큰”이라는 점이 명확해진다.
