Cumulative CTS 아이디어 정리

기존의 per-slot CTS를 cumulative / window CTS로 일반화하는 아이디어를 정리한 문서다. 핵심은 receiver-driven admission은 유지하되, control granularity를 바꿔 reverse control overhead와 sender stall을 줄이는 것이다.

Topic: receiver-driven admission
Focus: per-slot CTS vs cumulative CTS
Context: NCCL / IB transport / slot pipeline

1. 문제의식

기존 per-slot CTS는 receiver가 slot 하나를 비울 때마다, 그 slot 하나에 대한 CTS(addr, rkey, size, idx)를 sender에게 보낸다. 이 구조는 가장 정확하지만, 데이터 진행 단위와 control 단위가 거의 1:1로 묶인다는 문제가 있다.

Per-slot CTS receiver frees slot k -> send CTS(k) -> sender waits for CTS(k) -> sender sends data for slot k -> repeat Cumulative CTS receiver has W free slots -> send one grant: [k, k+W-1] -> sender can keep sending inside this window -> receiver extends grant later
핵심 차이는 receiver-driven 여부가 아니라, receiver가 grant를 어느 granularity로 발급하느냐다.

2. Cumulative CTS의 핵심 아이디어

receiver는 더 이상 매 slot마다 CTS를 보내지 않고, 미래의 연속된 slot 구간에 대해 하나의 누적 grant를 보낸다. sender는 그 범위 안에서는 추가 CTS 없이 계속 전송한다.

Per-slot CTS

  • CTS 1개 = slot 1개 허가
  • 정밀도는 높지만 control 빈도가 높다
  • reverse path 지연에 민감하다

Cumulative CTS

  • CTS 1개 = 여러 slot window 허가
  • control 빈도를 낮출 수 있다
  • sender pipeline을 덜 자주 끊는다
receiver-driven admission의 철학은 그대로 유지된다. sender가 자율적으로 보내는 것이 아니라, 여전히 receiver가 grant_until을 결정한다.

3. 기대되는 장점

Control Messages
감소

slot마다 보내던 CTS를 window 단위로 줄일 수 있다.

Sender Stall
완화

reverse control 지연이 곧바로 send idle로 이어지는 빈도를 줄인다.

Pipeline Occupancy
향상

여러 slot을 미리 열어두어 steady-state를 더 잘 유지할 수 있다.

Policy Knob
확장

W를 조절해 conservative/aggressive admission을 연속적으로 바꿀 수 있다.

3.1 CTS 패킷 수 관점

이상적으로는 grant window가 W라면, 동일한 총 전송량에 대해 CTS 수를 대략 1/W 수준으로 줄일 수 있다.

총 slot 수 Per-slot CTS Cumulative CTS (W=4) Cumulative CTS (W=8)
64 64 CTS 16 CTS 8 CTS
128 128 CTS 32 CTS 16 CTS
실제 수치는 partial grant, peer skew, slot reuse timing 때문에 달라질 수 있다. 위 표는 직관을 위한 단순 모델이다.

4. 왜 좋은가

4.1 reverse control path 부담 완화

기존 구조는 data path가 아니라 control path의 작은 지연에도 민감하다. receiver가 slot을 비웠더라도 CTS가 늦게 도착하면 sender는 다음 전송을 못 한다. cumulative CTS는 sender가 이미 받은 grant 범위 안에서 계속 보낼 수 있게 만들어, reverse path jitter를 흡수한다.

4.2 bounded pipeline 유지

NCCL의 slot pipeline은 유한 깊이의 파이프라인이다. 좋은 throughput은 pipeline depth만큼 slot이 미리 열려 있을 때 나온다. cumulative CTS는 receiver가 free slot 수를 기반으로 한 번에 여러 slot을 열어둘 수 있게 한다.

4.3 collective-aware policy와 결합 가능

grant window W는 workload semantics를 반영하는 좋은 정책 파라미터가 된다.

  • AllToAll + Simple: incast burst를 줄이기 위해 W를 작게
  • AllReduce + Ring + LL: pipeline 유지가 중요하므로 W를 크게
  • receiver free slots가 충분하지 않으면 W 축소
  • contention이 낮으면 W 확대

5. Per-Slot CTS 의사코드

struct CTS { uint64_t idx; uint64_t addr; uint32_t rkey; size_t size; }; // receiver void issue_cts_for_one_slot(int slot, uint64_t idx) { CTS msg; msg.idx = idx; msg.addr = recv_slot_addr(slot); msg.rkey = recv_slot_rkey(slot); msg.size = recv_slot_size(slot); rdma_write_to_sender_cts_fifo(slot, msg); } // sender void try_send_one_slot(int slot, uint64_t expected_idx) { if (!gpu_local_slot_ready(slot)) return; if (!cts_fifo[slot].valid) return; if (cts_fifo[slot].idx != expected_idx) return; rdma_write_data(local_slot_addr(slot), cts_fifo[slot].addr, cts_fifo[slot].rkey, min(local_slot_size(slot), cts_fifo[slot].size)); }
장점은 가장 정확하다는 점이고, 단점은 slot마다 reverse control을 요구한다는 점이다.

6. Proposed Cumulative CTS 의사코드

struct CumulativeCTS { uint64_t epoch; uint64_t grant_from_idx; uint64_t grant_until_idx; uint64_t recv_base_addr; uint32_t rkey; size_t step_size; }; // receiver void try_extend_grant() { int free_slots = count_free_recv_slots(); int W = compute_grant_window(collAPI, algorithm, protocol, free_slots); uint64_t new_grant_until = min(next_idx + W - 1, max_receivable_idx()); if (new_grant_until <= grant_until_idx) return; CumulativeCTS msg; msg.epoch = epoch; msg.grant_from_idx = grant_until_idx + 1; msg.grant_until_idx = new_grant_until; msg.recv_base_addr = recv_slot_base_addr(); msg.rkey = recv_slot_rkey_base(); msg.step_size = recv_step_size(); send_cumulative_cts(msg); grant_until_idx = new_grant_until; } // sender void try_send() { if (local_send_idx > remote_grant_until) return; int local_slot = (local_send_idx - 1) % NCCL_STEPS; if (!gpu_local_slot_ready(local_slot)) return; int remote_slot = (local_send_idx - 1) % NCCL_STEPS; uint64_t remote_addr = remote_base_addr + remote_slot * remote_step_size; rdma_write_data(local_slot_addr(local_slot), remote_addr, remote_rkey, local_slot_size(local_slot)); local_send_idx++; }
이 설계는 receiver free slots 기반 receiver-driven admission을 유지하면서, control granularity만 slot 단위에서 window 단위로 바꾼다.

7. 정책 파라미터 예시

cumulative CTS의 핵심 제어 변수는 grant window W다. 이 값을 정적으로 둘 수도 있고, workload-aware policy로 동적으로 바꿀 수도 있다.

파라미터 의미 W에 주는 영향
collAPI AllReduce, AllToAll, AllGather 등 AllToAll은 incast 위험이 크므로 보수적으로
algorithm/pattern Ring, Tree, PAT, P2P-expanded AllToAll fan-in/fan-out 구조에 따라 조정
protocol Simple, LL, LL128 Simple은 burst가 크므로 작은 window가 유리
free_slots receiver-side available credit 실제 grant의 상한
active_senders AllToAll류에서 동시에 들어오는 sender 수 aggregate incast 위험이 클수록 축소

8. 언제 효과가 클까

효과가 큰 경우

  • inter-node RDMA / RoCE 환경
  • AllToAll, Gather/Scatter처럼 fan-in 또는 many-to-many가 큰 경우
  • Simple protocol 비중이 큰 큰 메시지
  • reverse control path 지연이 sender idle로 이어지는 경우

효과가 제한적이거나 주의가 필요한 경우

  • low-contention 환경
  • 작은 메시지
  • grant를 너무 크게 잡아 다시 burst를 키우는 경우
  • direct/register path처럼 recv target이 규칙적이지 않은 경우

9. tradeoff

  • 장점: CTS 패킷 수 감소, reverse path overhead 감소, sender stall 완화, pipeline occupancy 향상
  • 단점: grant를 너무 일찍 많이 주면 per-slot CTS보다 admission 정밀도가 떨어질 수 있음
  • 구현 난이도: staged path는 비교적 쉽고, direct/register path는 hybrid metadata 방식이 필요할 수 있음
  • 논문 관점: 단순 piggyback보다 “receiver-driven admission의 control granularity를 적응적으로 바꾼다”는 framing이 더 좋음
따라서 이 아이디어의 핵심 claim은 “항상 throughput이 증가한다”가 아니라, “receiver-driven semantics를 유지하면서 control frequency를 낮추고, 적절한 W 선택 시 congested case에서 goodput과 stability를 개선한다”가 되어야 한다.

10. 한 문장 요약

Cumulative CTS는 기존의 per-slot CTS를 여러 slot에 대한 bounded future grant로 일반화한 방식이며, receiver-driven admission은 유지한 채 control overhead와 sender idle을 줄이기 위한 설계다.
