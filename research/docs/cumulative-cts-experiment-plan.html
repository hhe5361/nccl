Experiment Plan

Cumulative CTS 실험 계획서

NCCL 기반 receiver-driven admission에서 per-slot CTS를 cumulative CTS로 일반화했을 때의 효과를 검증하기 위한 실험 계획 문서다. 목적, 아이디어, 설계, 기대효과, 세부 실험 단계, 수집 데이터, 시각화, 유사 연구 대비 포지셔닝을 한 번에 정리한다.

Cluster: 8 nodes
Topology: 2 racks × 4 nodes, Clos
Network: RoCE v2 RDMA
Target: NCCL / proxy / IB transport

1. 목적

이 연구의 목적은 현재 NCCL/IB transport의 per-slot CTS 기반 receiver-driven admission을 cumulative CTS로 확장했을 때, control overhead를 줄이면서도 congested 환경에서 성능과 안정성을 개선할 수 있는지 입증하는 것이다.

P1. 기본 효과

CTS 패킷 수와 CTS 바이트 수가 실제로 줄어드는가.

P2. 원인 분석

collective / algorithm / protocol 조합에 따라 burst와 incast 정도가 실제로 달라지는가.

P3. 정책 효과

그 차이를 이용해 parameter-aware cumulative CTS를 적용하면 baseline 대비 이득이 있는가.

핵심은 단순히 CTS 수가 줄었다가 아니라, 어떤 workload에서 왜 줄여도 안전한지와 어떤 workload에서는 보수적으로 줄여야 하는지를 같이 보여주는 것이다.

2. 핵심 아이디어

baseline은 receiver가 free slot 하나가 생길 때마다 해당 slot에 대한 CTS를 sender에게 보낸다. 제안 방식은 receiver가 미래의 연속된 slot 구간에 대한 grant를 한 번에 보내고, 이 grant window W를 collective type, algorithm, protocol, 그리고 receiver-side slot occupancy에 따라 동적으로 조정한다.

Baseline free slot 1개 발생 -> CTS 1개 송신 -> sender가 slot 1개 전송 -> 반복 Proposed free slots 존재 -> cumulative CTS로 [idx, idx+W-1] grant -> sender는 grant window 안에서 연속 전송 -> occupancy가 높아지면 다음 grant의 W 축소 -> occupancy가 낮아지면 W 확대
이 연구의 핵심 설계 포인트는 grant를 크게 주면 burst가 커질 수 있다는 점이다. 그래서 무조건 큰 W가 아니라, parameter-aware + occupancy-aware bounded cumulative CTS가 필요하다.

3.1 설계 변형

Variant 설명 목적
B0 Stock NCCL per-slot CTS baseline
B1 Static cumulative CTS, fixed W control overhead 감소의 순수 효과 확인
B2 Adaptive cumulative CTS, W=f(collAPI, algorithm, protocol, occupancy) parameter-aware policy의 효과 검증
B3 Adaptive cumulative CTS + high/low watermark hysteresis burst amplification 방지

4. 구조 설계 의사코드

4.1 정책 함수

int choose_window(collAPI, algorithm, protocol, free_slots, occ_slots, active_senders) { int W = 1; // semantic prior if (collAPI == ALLREDUCE && algorithm == RING && protocol != SIMPLE) W = 4; if (collAPI == ALLREDUCE && protocol == SIMPLE) W = 2; if (collAPI == ALLGATHER || collAPI == REDUCESCATTER) W = 2; if (collAPI == ALLTOALL) W = 1; // protocol prior if (protocol == LL || protocol == LL128) W += 1; if (protocol == SIMPLE) W = min(W, 2); // incast pressure if (active_senders >= 4) W = min(W, 2); if (active_senders >= 6) W = 1; // occupancy-aware throttling if (occ_slots >= HIGH_WATERMARK) W = 1; else if (occ_slots <= LOW_WATERMARK) W = min(W + 1, WMAX); // final cap W = min(W, free_slots); W = max(W, 1); return W; }

4.2 receiver-side cumulative CTS

void try_issue_cumulative_cts(receiver_state* st, flow_ctx* f) { int free_slots = st->maxDepth - st->occSlots; int W = choose_window(f->collAPI, f->algorithm, f->protocol, free_slots, st->occSlots, st->activeSenders); uint64_t new_grant_until = min(f->nextIdx + W - 1, f->maxReceivableIdx); if (new_grant_until <= f->grantUntil) return; CumulativeCTS msg; msg.epoch = f->epoch; msg.grant_from_idx = f->grantUntil + 1; msg.grant_until_idx = new_grant_until; msg.recv_base_addr = f->recvBase; msg.rkey = f->recvRkey; msg.step_size = f->stepSize; msg.W = W; send_cumulative_cts(msg); f->grantUntil = new_grant_until; }

4.3 sender-side send gate

void try_send(sender_state* st, flow_ctx* f) { if (f->sendIdx > f->remoteGrantUntil) return; if (!local_slot_ready(f->sendIdx)) return; int local_slot = (f->sendIdx - 1) % NCCL_STEPS; int remote_slot = (f->sendIdx - 1) % NCCL_STEPS; uint64_t remote_addr = f->remoteBase + remote_slot * f->remoteStepSize; rdma_write(local_slot_addr(local_slot), remote_addr, f->remoteRkey, local_slot_size(local_slot)); f->sendIdx++; }
이미 발급된 grant는 즉시 revoke하기 어렵다. 따라서 정책은 window reset보다 future grant shrink + high/low watermark hysteresis 형태가 더 현실적이다.

5. 기대효과

CTS Messages
감소

slot당 1개에서 window당 1개로 granularity 축소.

Reverse Path Stall
완화

control path jitter가 sender idle로 직결되는 빈도 감소.

Pipeline Occupancy
향상

bounded pipeline이 더 잘 채워질 가능성.

Congestion Awareness
강화

AllToAll 등 incast-prone workload에서 더 보수적 admission 가능.

단, W가 너무 크면 burst가 커지고 queue buildup이 늘 수 있다. 논문에서 반드시 보여줘야 하는 것은 효과뿐 아니라 안전하게 제한했기 때문에 효과가 난다는 점이다.

6. 입증해야 할 가설

ID 가설 입증 방법
H1 Cumulative CTS는 baseline 대비 CTS 패킷 수와 CTS 바이트 수를 유의미하게 줄인다. internal counters + per-op 로그 비교
H2 burst/incast 강도는 collective, algorithm, protocol에 따라 다르다. fan-in, burst size, ingress rate, slot occupancy, queue-related counters 수집
H3 parameter-aware cumulative CTS는 high-risk 조합에서 stock NCCL보다 goodput과 tail latency를 개선한다. latency CDF, throughput, p95/p99, job completion time 비교
H4 low-contention 조합에서는 성능 regression이 제한적이다. benign case에서 throughput 및 latency regression 측정
H5 cross-rack Clos 구간에서 효과가 intra-rack보다 크다. 4-node intra-rack vs 8-node cross-rack 비교

8. 실험 단계

Phase 0. Correctness / Instrumentation

  1. baseline과 modified NCCL 모두에서 collective 결과 일치 검증
  2. deadlock, timeout, data corruption 여부 검증
  3. CTS issue, grant_until, slot occupancy, send/recv step 로그 추가

Phase 1. Baseline traffic characterization

  1. stock NCCL로 collective × algorithm × protocol × size sweep
  2. 각 조합에서 burst size, active senders, receiver ingress rate, slot occupancy, CTS count 측정
  3. 어떤 조합이 실제로 incast-prone인지 정량화

Phase 2. Static cumulative CTS 효과

  1. W=2,4,8 sweep
  2. CTS packet/byte 감소율 측정
  3. sender stall 감소 여부 확인
  4. burst amplification과 throughput/latency tradeoff 확인

Phase 3. Parameter-aware policy

  1. collAPI/algorithm/protocol 기반 initial window policy 적용
  2. high-risk 조합에 보수적 window, low-risk 조합에 공격적 window 적용
  3. static cumulative보다 더 좋은 tradeoff가 나오는지 확인

Phase 4. Occupancy-aware hysteresis

  1. receiver slot occupancy에 high/low watermark 적용
  2. high watermark 초과 시 future grant shrink
  3. low watermark 이하에서만 window 재확장
  4. oscillation과 burst 억제 효과 측정

Phase 5. Clos-specific evaluation

  1. 4-node intra-rack와 8-node cross-rack 비교
  2. cross-rack 구간에서 효과가 더 큰지 확인
  3. dual concurrent jobs로 oversubscription 유사 상황 재현

Phase 6. Ablation

  1. semantic-only policy vs occupancy-only policy vs combined policy
  2. global budget only vs per-peer cap only vs combined cap
  3. watermark 없는 cumulative vs watermark 있는 cumulative

12. 비슷한 아이디어와 차별점

credit, grant, receiver-driven scheduling 자체는 기존 datacenter transport 문헌에 많이 존재한다. novelty는 그 일반 개념 자체가 아니라, 이를 NCCL-like GPU collective runtime에 collective-aware cumulative CTS로 옮기는 데 있다.

작업 핵심 아이디어 이 연구와의 관계
ExpressPass (2017) credit-scheduled congestion control credit 기반 proactive admission의 출발점. collective-aware는 아님.
Homa (2018) receiver-driven transport + dynamic priority receiver-managed grant와 overcommitment 철학이 유사. NCCL slot pipeline과는 다름.
Aeolus (2022) pre-credit phase 최적화 credit/control phase 자체를 성능 병목으로 본다는 점이 유사.
FastCredit (2022) credit transmission scheduling credit도 scheduling 대상이라는 점이 유사. collective semantics는 사용하지 않음.
SIRD (2025) receiver-driven + sender capacity feedback receiver scheduling을 richer signal로 조정한다는 점이 유사.
FAST (2026) All-to-All scheduling with incast avoidance motivation이 강하게 겹침. 하지만 schedule synthesis이며 CTS/grant policy는 아님.
현재 NCCL IB CTS recv target ready 시 per-slot CTS baseline. cumulative도 아니고 collective-aware policy도 아님.
따라서 안전한 claim은 “credit/grant 자체를 처음 제안한다”가 아니라, collective/API/protocol semantics를 이용해 NCCL의 per-slot CTS를 cumulative CTS로 일반화한 첫 실험적 설계에 가깝다.

참고 자료: ExpressPass, Homa, Aeolus, FastCredit, SIRD, FAST.

13. 논문에 넣을 실험 메시지

  1. 기본 사실: cumulative CTS는 control overhead를 줄인다.
  2. 중간 사실: collective/algorithm/protocol에 따라 burst와 incast 위험은 실제로 다르다.
  3. 핵심 사실: 그 차이를 이용한 parameter-aware cumulative CTS는 고위험 조합에서 더 좋은 tradeoff를 낸다.
  4. 안전성 사실: watermark-aware shrink가 없다면 naive cumulative는 burst를 키울 수 있다.
즉 논문의 구조는 “control 절감” → “traffic shape 차이 입증” → “shape-aware policy 효과” → “안전장치 필요성” 순서가 가장 설득력 있다.
