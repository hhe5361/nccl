Phase 1 / B1

Static Fake Cumulative 구현 및 실험 계획

B1의 목적은 wire format을 바꾸지 않고 receiver proxy가 미리 열어두는 recv depth를 고정 W = 1, 2, 4, 8로 제한하는 것이다. 이 단계는 CTS packet 수 감소 실험이 아니라, window shaping이 burst / occupancy / throughput에 주는 영향을 보는 단계다.

Main implementation: fake cumulative
Sweep: W=1,2,4,8
Cluster: 8 nodes / 2 racks / Clos / RoCE v2
Deployment target: custom NCCL + nccl-tests or PyTorch DDP

1. B1에서 정확히 바꾸는 것

바꾸는 것

receiver proxy와 send proxy가 동시에 열어둘 수 있는 effective window를 고정값 W로 제한한다.

안 바꾸는 것

IB CTS packet format, ncclIbSendFifo, ncclIbPostFifo() 경로는 그대로 둔다.

의미

CTS는 여전히 per-slot로 발급되지만, receiver가 미리 여는 step 수를 제한해서 aggregate inflight burst를 shaping한다.

즉 B1은 "real cumulative CTS"가 아니라 static recv-post / CTS window shaping이다. 현재 구현은 receiver-only W_eff를 사용한다. 즉 recvProxyProgress()만 W_eff로 제한하고, sendProxyProgress()는 stock depth를 유지한다.

3. 실제 코드 변경 포인트

3.1 새 파라미터 추가

NCCL_PARAM(Phase1StaticW, "PHASE1_STATIC_W", 0);

해석:

  • 0 또는 unset: stock NCCL 동작
  • 1,2,4,8: B1 static fake cumulative depth

3.2 helper 추가

baseDepth = min(NCCL_STEPS, NCCL_SHARED_STEPS / args->nsubs) cfgW = ncclParamPhase1StaticW() W_eff = (cfgW > 0) ? max(1, min(baseDepth, cfgW)) : baseDepth

현재 B1에서는 이 helper를 recv proxy admission window 계산에만 쓴다. send proxy는 stock baseDepth를 그대로 유지한다.

3.3 sendProxyProgress() 수정

수정 포인트:

  • B1 recv-only revision에서는 send proxy를 stock NCCL 동작으로 되돌린다.
  • sub->posted < sub->done + baseDepth를 유지한다.
  • sharedBuffSlot = sub->posted % baseDepth를 유지한다.
  • PROXY_SEND_WSTALL는 더 이상 B1 핵심 지표가 아니다. send-side local throttling을 실험에서 제거한다.

3.4 recvProxyProgress() 수정

수정 포인트:

  • int maxDepth = ...를 int W_eff = ...로 치환
  • sub->posted >= sub->done + maxDepth를 ... + W_eff로 변경
  • sharedBuffSlot = sub->posted % maxDepth를 % W_eff로 변경
  • window 때문에 더 못 여는 경우 PROXY_RECV_WSTALL 로그 추가

3.5 기존 로그 확장

현재 phase0ProxyLog()에는 base/posted/received/transmitted/done만 있다. B1에서는 아래 필드를 추가하는 것이 좋다.

tNs= wBase= wCfg= wEff= occPd=posted-done occTr=transmitted-done

tNs는 clockNano()를 사용하면 된다.

4.5 Phase 0 / Phase 1 이벤트 로그 상세 설명

B1 실험에서 실제로 쓰는 로그는 PHASE0와 PHASE1 두 계층이다. PHASE0는 기존 proxy / transport 진행 상태를 관찰하기 위한 로그이고, PHASE1는 static window 실험에서 추가한 window 설정 / stall 로그다.

4.5.1 공통 해석 원칙

  • PHASE0는 “실제 데이터 / control path가 어디까지 진행됐는가”를 보여준다.
  • PHASE1는 “window 때문에 왜 더 못 나아갔는가”를 보여준다.
  • 현재 B1은 receiver-only control이므로, PHASE1의 핵심 stall 로그는 PROXY_RECV_WSTALL이다.
  • posted, received, transmitted, done은 모두 step frontier다. slot 주소 포인터가 아니다.
  • slot은 보통 (base + frontier) % NCCL_STEPS로 계산된 현재 물리 slot이다.
  • occPd = posted - done, occTr = transmitted - done은 proxy 입장에서 현재 outstanding depth를 보는 지표다.
중요: “빈 slot을 직접 스캔해서 CTS를 보내는가?”에 대한 답은 아니다. 현재 구현은 conn.buffs[]를 훑어서 빈칸을 찾는 구조가 아니라, recvProxyProgress()가 posted < done + W_eff 조건을 만족할 때 다음 recv를 post하고, 그 결과로 ncclNet->irecv()가 호출되며, IB 경로에서는 그 시점에 IB_CTS_ISSUE가 발생한다.

4.5.3 이벤트별 상세 설명

이벤트 계층 발생 위치 정확한 의미 실험 해석
PROXY_WINDOW_CFG PHASE1 recvProxyProgress() 시작부 receiver-side sub op에서 이번에 어떤 window가 적용됐는지 1회 기록 wBase, wCfg, wEff sanity check용. recv admission이 의도대로 걸렸는지 확인하는 첫 로그
PROXY_RECV_WSTALL PHASE1 recvProxyProgress() posted >= done + W_eff라서 receiver 쪽에서 더 이상 새로운 recv를 post하지 못함 B1의 핵심 제어 효과를 직접 보여주는 로그. recv window가 실제로 얼마나 자주 bind되는지 측정
PROXY_SEND_POST PHASE0 sendProxyProgress()에서 ncclNet->isend() 성공 직후 sender proxy가 현재 slot payload를 NIC/transport에 실제로 post했음 데이터 plane send injection 이벤트. size 합으로 send burst를 계산
PROXY_SEND_DONE PHASE0 sendProxyProgress()에서 ncclNet->test() 완료 후 보낸 step이 transport 완료되어 slot을 recycle 가능하게 됨 sender 측 completion frontier. done 증가와 함께 credit 반환을 의미
PROXY_RECV_POST PHASE0 recvProxyProgress()에서 ncclNet->irecv() 성공 직후 receiver proxy가 다음 recv target을 열었음 IB path에서는 이 직후 IB_CTS_ISSUE가 이어진다. “CTS는 빈 slot 스캔 이벤트가 아니라 recv post 결과”라는 점이 중요
PROXY_RECV_NET_DONE PHASE0 recvProxyProgress()에서 ncclNet->test() 완료 후 NIC 입장에서 해당 recv step의 데이터 도착이 완료됨 network receive completion. 아직 GPU가 볼 수 있는 상태는 아니다
PROXY_RECV_VISIBLE PHASE0 recvProxyProgress()에서 recvTail을 밀어준 직후 도착한 데이터를 GPU가 읽을 수 있도록 publish함 recv path에서 “network done”과 “GPU visible”을 구분해준다. flush/GDR 영향이 이 사이에 들어간다
PROXY_RECV_CONSUMED PHASE0 recvProxyProgress()에서 sendMem->head 확인 후 GPU가 해당 step을 실제로 소비 완료해서 slot을 recycle할 수 있게 됨 receiver-side credit return. 이 이벤트가 있어야 done이 전진하고 window가 다시 열린다
IB_CTS_ISSUE PHASE0 / IB ncclIbPostFifo() receiver가 sender의 CTS FIFO로 RDMA write를 날려 recv target(addr/rkey/size/idx)을 광고함 reverse control path 핵심 이벤트. 총 개수보다 tNs 기반 시간 분포와 send post와의 거리 해석이 중요
IB_SEND_POST PHASE0 / IB ncclIbMultiSend() 성공 후 sender가 matching CTS를 확인하고 실제 IB send / RDMA write를 올림 실제 fabric injection 이벤트. burst size 계산은 주로 이 로그 기준으로 한다
IB_SEND_COMPLETE PHASE0 / IB ncclIbRequestComplete() IB send request completion IB transport 차원의 완료. proxy의 PROXY_SEND_DONE와 함께 보면 send completion chain을 해석할 수 있다

4.5.4 정상 경로에서의 시간축 순서

recvProxyProgress() -> PHASE1 PROXY_WINDOW_CFG -> PHASE0 PROXY_RECV_POST -> PHASE0 IB_CTS_ISSUE sendProxyProgress() -> PHASE0 IB_SEND_POST -> PHASE0 PROXY_SEND_POST -> PHASE0 IB_SEND_COMPLETE -> PHASE0 PROXY_SEND_DONE recvProxyProgress() -> PHASE0 PROXY_RECV_NET_DONE -> PHASE0 PROXY_RECV_VISIBLE -> PHASE0 PROXY_RECV_CONSUMED

위 순서는 “대표적인” 정상 경로다. 실제 로그에서는 여러 sub, channel, peer가 겹쳐서 섞여 보인다. 그래서 해석할 때는 항상 peer, channel, slot, reqId를 같이 봐야 한다.

4.5.5 B1 해석에서 특히 중요한 이벤트

  • PROXY_WINDOW_CFG: 이번 run에서 실제로 어떤 wEff가 걸렸는지 확인
  • PROXY_RECV_WSTALL: 작은 W가 receiver admission을 얼마나 자주 막았는지 측정
  • IB_SEND_POST: 실제 send injection burst 계산의 기준
  • PROXY_RECV_POST: receiver가 얼마나 공격적으로 미리 recv를 열었는지 측정
  • PROXY_RECV_CONSUMED: window가 실제로 다시 열리는 속도 측정
이번 B1은 fake cumulative이므로 IB_CTS_ISSUE 총 개수 자체는 거의 바뀌지 않을 수 있다. 대신 언제 얼마나 몰려서 PROXY_RECV_POST, IB_CTS_ISSUE, IB_SEND_POST가 발생하는지와 WSTALL, occPd, occTr를 같이 봐야 한다.

8. B1 해석 기준

W=1

가장 보수적이다. burst는 가장 작아져야 하지만 throughput 손실이 가장 크다.

W=2

high-risk workload에서 타협점이 될 가능성이 높다.

W=4

중간 위험 workload에서 균형점이 될 가능성이 높다.

W=8

stock과 가장 가깝다. throughput은 좋지만 burst/occupancy가 가장 높을 가능성이 크다.

B1의 결론은 "어떤 W가 항상 최고다"가 아니다. best fixed W is workload-dependent를 입증하는 것이 Phase 1의 목적이다.
따라서 논문 메시지는 "B1이 정답"이 아니라, B1 결과가 B2/B3 adaptive policy의 필요성을 만든다로 써야 한다.

10. Deploy 요약

10.1 추천 방식

기존 [deploy scripts](/mnt/c/users/hyoeun/dev/nccl/research/code/deploy/README.md) 기반으로 custom NCCL을 빌드한 뒤, nccl-tests 또는 PyTorch DDP에서 LD_PRELOAD 또는 source-built PyTorch로 실험하는 것이 가장 안전하다.

10.2 간단한 deploy 절차

  1. 실험 브랜치를 worker 노드에 배포
  2. custom NCCL 빌드
  3. nccl-tests 또는 PyTorch 환경에서 custom libnccl.so 링크
  4. NCCL_PHASE0_LOG=1, NCCL_PHASE1_STATIC_W=<1|2|4|8> 설정
  5. NCCL_DEBUG_FILE를 NFS 경로로 지정
