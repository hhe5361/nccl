Phase 1 / B1

Static Fake Cumulative 구현 및 실험 계획

B1의 목적은 wire format을 바꾸지 않고 receiver proxy가 미리 열어두는 recv depth를 고정 W = 1, 2, 4, 8로 제한하는 것이다. 이 단계는 CTS packet 수 감소 실험이 아니라, window shaping이 burst / occupancy / throughput에 주는 영향을 보는 단계다.

Main implementation: fake cumulative
Sweep: W=1,2,4,8
Cluster: 8 nodes / 2 racks / Clos / RoCE v2
Deployment target: custom NCCL + nccl-tests or PyTorch DDP

1. B1에서 정확히 바꾸는 것

바꾸는 것

receiver proxy와 send proxy가 동시에 열어둘 수 있는 effective window를 고정값 W로 제한한다.

안 바꾸는 것

IB CTS packet format, ncclIbSendFifo, ncclIbPostFifo() 경로는 그대로 둔다.

의미

CTS는 여전히 per-slot로 발급되지만, receiver가 미리 여는 step 수를 제한해서 aggregate inflight burst를 shaping한다.

즉 B1은 "real cumulative CTS"가 아니라 static recv-post / CTS window shaping이다.

3. 실제 코드 변경 포인트

3.1 새 파라미터 추가

NCCL_PARAM(Phase1StaticW, "PHASE1_STATIC_W", 0);

해석:

  • 0 또는 unset: stock NCCL 동작
  • 1,2,4,8: B1 static fake cumulative depth

3.2 helper 추가

baseDepth = min(NCCL_STEPS, NCCL_SHARED_STEPS / args->nsubs) cfgW = ncclParamPhase1StaticW() W_eff = (cfgW > 0) ? max(1, min(baseDepth, cfgW)) : baseDepth

이 helper는 send/recv proxy 양쪽에서 같은 값을 써야 한다. shared buffer 경로가 posted % depth에 의존하기 때문이다.

3.3 sendProxyProgress() 수정

수정 포인트:

  • int maxDepth = ...를 int W_eff = ...로 치환
  • sub->posted < sub->done + maxDepth를 ... + W_eff로 변경
  • sharedBuffSlot = sub->posted % maxDepth를 % W_eff로 변경
  • window 때문에 더 못 여는 경우 PROXY_SEND_WSTALL 로그 추가

3.4 recvProxyProgress() 수정

수정 포인트:

  • int maxDepth = ...를 int W_eff = ...로 치환
  • sub->posted >= sub->done + maxDepth를 ... + W_eff로 변경
  • sharedBuffSlot = sub->posted % maxDepth를 % W_eff로 변경
  • window 때문에 더 못 여는 경우 PROXY_RECV_WSTALL 로그 추가

3.5 기존 로그 확장

현재 phase0ProxyLog()에는 base/posted/received/transmitted/done만 있다. B1에서는 아래 필드를 추가하는 것이 좋다.

tNs= wBase= wCfg= wEff= occPd=posted-done occTr=transmitted-done

tNs는 clockNano()를 사용하면 된다.

8. B1 해석 기준

W=1

가장 보수적이다. burst는 가장 작아져야 하지만 throughput 손실이 가장 크다.

W=2

high-risk workload에서 타협점이 될 가능성이 높다.

W=4

중간 위험 workload에서 균형점이 될 가능성이 높다.

W=8

stock과 가장 가깝다. throughput은 좋지만 burst/occupancy가 가장 높을 가능성이 크다.

B1의 결론은 "어떤 W가 항상 최고다"가 아니다. best fixed W is workload-dependent를 입증하는 것이 Phase 1의 목적이다.
따라서 논문 메시지는 "B1이 정답"이 아니라, B1 결과가 B2/B3 adaptive policy의 필요성을 만든다로 써야 한다.

10. Deploy 요약

10.1 추천 방식

기존 [deploy scripts](/mnt/c/users/hyoeun/dev/nccl/research/code/deploy/README.md) 기반으로 custom NCCL을 빌드한 뒤, nccl-tests 또는 PyTorch DDP에서 LD_PRELOAD 또는 source-built PyTorch로 실험하는 것이 가장 안전하다.

10.2 간단한 deploy 절차

  1. 실험 브랜치를 worker 노드에 배포
  2. custom NCCL 빌드
  3. nccl-tests 또는 PyTorch 환경에서 custom libnccl.so 링크
  4. NCCL_PHASE0_LOG=1, NCCL_PHASE1_STATIC_W=<1|2|4|8> 설정
  5. NCCL_DEBUG_FILE를 NFS 경로로 지정
  6. run metadata와 raw logs를 함께 저장

10.3 예시 환경변수

export NCCL_PHASE0_LOG=1 export NCCL_PHASE1_STATIC_W=4 export NCCL_DEBUG=INFO export NCCL_DEBUG_SUBSYS=NET export NCCL_DEBUG_FILE=/mnt/nfs_share/cts_experiments/phase1_YYMMDD_HHMMSS/W4/<workload>/worker%h/nccl.%p.log # protocol / algorithm sweep export NCCL_ALGO=Ring export NCCL_PROTO=Simple

10.4 주의점

  • PyTorch DDP로 돌릴 경우 실제로 custom NCCL이 로드됐는지 반드시 확인
  • 모든 노드에서 같은 commit / 같은 env로 실행
  • placement가 바뀌지 않도록 hostfile 또는 rank mapping을 고정
요약
B1은 static fake cumulative window sweep 단계다. 구현 핵심은 send/recv proxy의 effective window를 W=1,2,4,8로 제한하는 것이고, 실험 핵심은 throughput 자체보다 burst / occupancy / throughput tradeoff를 보는 것이다.
